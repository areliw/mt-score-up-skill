# ดีบักอย่างมีวินัย หา root cause

โค้ด/สคริปต์พังแล้วงงว่า "ผิดตรงไหน" → skill นี้วางลำดับไล่บั๊กให้เจอ *สาเหตุจริง* ไม่ใช่เดาแล้วแปะแก้จนพังเพิ่ม

> **กฎข้อ 1:** ทุ่ม reproduce ก่อนเสนอวิธีแก้ — repro คือ*ทางที่ดีสุด* (วัด fix ได้ชัด) **แต่ไม่ใช่เงื่อนไขบังคับ**: บั๊กที่ reproduce ไม่ได้ (heisenbug/prod-only/intermittent) ยัง diagnose ได้จาก **log/core dump/trace/static analysis**. อย่ากระโดดเดาสาเหตุลอยๆ.
> **กับดักข้อ 1:** เดาสาเหตุเดียวแล้วรีบแก้เลย (anchoring). คนเก่งสุดก็ติดกับนี้ — เห็น error แล้วปักใจว่า "ต้องเพราะ X" ทั้งที่ยังไม่ได้พิสูจน์. ของที่ทำให้เจอบั๊กเร็วจริงคือ **repro ที่กด pass/fail ได้ใน 2-5 วิ + ตั้งสมมติฐาน 3-5 อันแล้วลอง *หักล้าง* ก่อน** ไม่ใช่จ้องโค้ดเฉยๆ.

## ใช้เมื่อ
- สคริปต์/โน้ตบุ๊ก/ระบบพัง โยน error, ผลเพี้ยน, หรือช้าลงผิดปกติ (perf regression)
- หาสาเหตุไม่เจอ แก้ไปหลายรอบแล้วยังพังเหมือนเดิม
- บั๊ก "บางทีพัง บางทีไม่" (flaky) — กดซ้ำแล้วผลไม่นิ่ง
- งาน data: ผล analysis เปลี่ยนระหว่างรัน, model accuracy ตก, pipeline พังเงียบๆ
- ก่อนจะบอกว่า "แก้เสร็จแล้ว" — อยากมั่นใจว่าซ่อมถูกจุดจริง

## วิธีใช้
วาง skill นี้ + แปะ error / อธิบายอาการ + โค้ดที่เกี่ยวข้อง → AI จะพาไล่เป็นลำดับ: สร้าง repro → หา fail path → ตั้ง+หักล้างสมมติฐาน → แก้ + กันบั๊กกลับ. ตอบทีละชั้น อย่ารวบ.

## ลำดับไล่บั๊ก (ทำตามขั้น อย่าข้าม)

| ขั้น | ทำอะไร | ผ่านเมื่อ |
|---|---|---|
| 1. Reproduce | ทำให้บั๊กเกิดซ้ำได้ด้วยคำสั่งเดียว/test เดียว | กดแล้วพังตามที่ user เจอ ทุกครั้ง (หรือ flaky → ดันอัตราให้สูงพอดีบัก) |
| 2. หา fail path | หา *จุด* ที่โค้ดพัง + *อะไร* คุมผลนั้น | รู้ว่าพลิก knob ไหนแล้วบั๊กขยับ |
| 3. ตั้ง+หักล้างสมมติฐาน | เขียน 3-5 อันแบบ falsifiable แล้วลองล้มก่อน | รอดการล้ม = **น่าเชื่อสุด** (fix แล้วหาย = สนับสนุน ไม่ใช่พิสูจน์เด็ดขาด) |
| 4. แก้ + regression test | แก้แล้วเขียน test กันบั๊กกลับ (ถ้ามี seam ที่ใช่) | repro เดิมไม่พังแล้ว + test เขียว |

### ขั้น 1 — Reproduce (หัวใจ ทุ่มแรงตรงนี้)
สร้าง **สัญญาณ pass/fail ที่เร็ว (1-5 วิ) + นิ่ง (deterministic)** ก่อนทำอย่างอื่น เรียงจากง่ายไปยาก:
1. **Test ที่ fail** ตรงจุดที่แตะบั๊กได้ (unit/integration)
2. **สคริปต์ CLI / curl** ป้อน input เดิม diff กับผลที่ถูก
3. **Replay ข้อมูลจริง** — เซฟ payload/HTML/log ที่ทำให้พัง แล้วยิงซ้ำผ่านโค้ดเดิม
4. **Harness จิ๋ว** — ตัดระบบเหลือชิ้นเดียวที่เรียกโค้ดบั๊กด้วยฟังก์ชันเดียว
5. **Fuzz/property loop** — บั๊ก "บางทีผิด" → ยิง 1000 input สุ่มหา pattern ที่พัง

> ทำให้ **นิ่ง:** pin เวลา, seed RNG, freeze network, แยก filesystem. loop 30 วิที่ flaky แทบไร้ค่า — loop 2 วิที่นิ่ง = ของขลัง.
> **Flaky:** เป้าไม่ใช่ repro สะอาด แต่คือ *ดันอัตราพังให้สูง* — loop 100×, ขนาน, อัด stress, แทรก sleep. 50% ดีบักได้, 1% ดีบักไม่ได้.
> **กดไม่ได้จริงๆ:** หยุด บอกตรงๆ ว่าลองอะไรไปบ้าง ขอ artifact (log dump / HAR / payload) หรือ env จาก user — **อย่า** เดาสาเหตุทั้งที่ยังไม่มี repro.

### ขั้น 2 — หา fail path (จุดพัง + อะไรคุมมัน)
1. **Debugger / `breakpoint()` ก่อน** ถ้า env รองรับ — 1 breakpoint ชนะ 10 print
2. **ไล่ code path + ลิสต์ knob** ที่มีผลต่อผลลัพธ์: config flag, env var, เงื่อนไข branch, รูปร่าง input, timing/concurrency → **พลิกทีละตัว**
3. **แทรก probe ในโค้ด** ถ้า knob ข้างนอกขยับบั๊กไม่ได้ — print ค่าตัวแปร ณ จุดสงสัย **ติด prefix เฉพาะ** เช่น `[DBG-a4f2]` เพื่อ grep ลบทีเดียวจบ
> **อ่าน traceback จากล่างขึ้นบน** (บรรทัดล่างสุด = error จริง). บั๊กมักซ่อนในจุดที่ "มั่นใจว่าถูก" ไม่ใช่จุดที่ error โผล่.
> **Perf regression:** print ไม่ช่วย — วัด baseline ก่อน (`performance.now()` / profiler / query plan) แล้ว bisect. **วัดก่อน แก้ทีหลัง.**

### ขั้น 3 — ตั้ง + หักล้างสมมติฐาน
- เขียน **3-5 อัน ไม่ใช่ 1** — สมมติฐานเดียว = ปักใจกับไอเดียแรกที่ดูเข้าท่า
- ทุกอันต้อง **falsifiable:** "ถ้า X เป็นเหตุ → พลิก Y บั๊กจะหาย / พลิก Z จะแย่ลง" บอก prediction ไม่ได้ = แค่ vibe ทิ้ง
- **รัน disproof ก่อน:** ออกแบบการทดลองที่ *ล้ม* สมมติฐานได้เร็วสุด — รอดการล้ม = **น่าเชื่อสุด** (ยังไม่ใช่พิสูจน์เด็ดขาด — fix แล้วบั๊กหายตามทำนาย = สนับสนุนแรง), ตาย = ตัดทิ้ง
- ลิสต์ให้ user ดูก่อนลอง — เขามักมี domain knowledge re-rank ทันที ("เพิ่ง deploy ตัวที่ 3")

### ขั้น 4 — แก้ + กันบั๊กกลับ
1. เขียน regression test **ก่อนแก้** — แต่ต้องมี **seam ที่ใช่** (test ยิงตรง pattern บั๊กจริง ไม่ใช่ตื้นเกิน)
2. **ไม่มี seam ที่ใช่ = นั่นคือ finding** — note ไว้ว่า architecture กันบั๊กไม่ได้ อย่าฝืนเขียน test หลอกตัวเอง
3. ดู test fail → แก้ → ดู test pass → รัน repro เดิม (un-minimised) ซ้ำให้แน่ใจ
4. **ก่อนปิดงาน:** repro เดิมไม่พังแล้ว · test เขียว · ลบ `[DBG-...]` ทุกอัน (grep prefix) · ลบ prototype ทิ้ง · เขียนสมมติฐานที่ถูกลง commit ให้คนถัดไปเรียนรู้

## VERDICT — เมื่อไหร่ข้ามทั้งหมดได้
บั๊ก trivial ที่ root cause ชัดจาก traceback ตรงๆ (พิมพ์ผิด 1 ตัว, ลืม `await`, KeyError จาก typo key) → แก้เลย ไม่ต้องครบ loop. **ใช้วิจารณญาณ** — วินัยนี้ไว้สำหรับบั๊กยาก/แก้แล้วพังซ้ำ/perf ตก ไม่ใช่ทุก typo.

## กับดัก (Anti-patterns)
- **เสนอแก้ก่อนมี repro** — แก้แบบไม่มีสัญญาณ pass/fail = เดามืด ถ้าจับได้ว่าตัวเองทำ ให้ถอยกลับขั้น 1
- **สมมติฐานเดียวแล้วรีบแก้** — anchoring กับไอเดียแรก; บังคับตัวเองเขียน 3-5 อัน + ล้มก่อน
- **พลิกหลาย knob พร้อมกัน** — บั๊กขยับแต่ไม่รู้เพราะตัวไหน; **เปลี่ยนทีละตัวแปร**
- **"log everything แล้ว grep"** — กลบสัญญาณ; probe ต้องตรงกับ prediction ของสมมติฐานเท่านั้น
- **ลืมลบ debug probe / print** — ค้างใน production; ติด prefix `[DBG-...]` ตั้งแต่แรกเพื่อ grep ลบ
- **บอก "แก้แล้ว" โดยไม่รัน repro เดิมซ้ำ** — แก้คนละบั๊กที่บังเอิญอยู่ใกล้ = แก้ผิดตัว verify ด้วย repro เดิมเสมอ
- **flaky แล้วยอมแพ้** — บั๊กเป็นๆ หายๆ ดีบักได้ ถ้าดันอัตราพังให้ถึง ~50% ก่อน อย่าปล่อยที่ 1%

## ช่องสำหรับผู้เชี่ยวชาญเติม
> เติมเคสจริงในสายงาน/โปรเจกต์คุณ เช่น:
> - *"(งาน data lab) บั๊กที่กัดบ่อยคือผลเพี้ยนเพราะ NaN/encoding/seed — ผม reproduce ด้วยการ..."*
> - *"สคริปต์ pipeline ผมเคยพังเงียบ ตอนหลังจับได้เพราะตั้ง repro แบบ..."*
> - *"perf ตกในงานผม ผมวัด baseline ด้วย... แล้ว bisect จาก..."*
