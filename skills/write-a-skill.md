# แพ็กวิจารณญาณของคุณเป็น skill

เปลี่ยน "ของในหัวคุณ" — เลือกอะไรเมื่อไหร่ + กับดักที่มือใหม่พลาด — ให้เป็นไฟล์ skill ที่ MT คนอื่นวางในแชต AI แล้วใช้ได้จริง

> **กฎข้อ 1:** skill = **วิจารณญาณ** (เลือกอะไรเมื่อไหร่ + พลาดตรงไหน) ไม่ใช่ความรู้. เทสต์ 1 ข้อก่อนเริ่ม: *"ถ้า Google/AI ตอบได้ทันทีในประโยคเดียว → นี่คือ reference doc ไม่ใช่ skill."* สิ่งที่ควรอยู่ใน skill คือสิ่งที่ AI ตอบกลางๆ แต่ **มือใหม่ยังเลือกผิด/พลาดกับดัก** อยู่ดี.
> **กับดักข้อ 1:** มือใหม่เขียน skill เป็น "ตำราย่อ" — ยัดนิยาม สูตร ตาราง normal range. นั่นคือ knowledge ที่ commodity AI รู้หมดแล้ว ไม่มีใครต้องการ skill มาบอกซ้ำ. ของที่มีค่าคือ **"เคสนี้เลือกทางไหน + ทำไมคนพลาดตรงนี้"** ซึ่งมาจากประสบการณ์คุณ ไม่ใช่ตำรา.

## ใช้เมื่อ
- คุณมี "ลูกเล่น/วิจารณญาณ" ในงานที่ทำซ้ำบ่อย แล้วอยากแพ็กให้คนอื่น (หรือ AI) ใช้ตามได้
- เห็นมือใหม่พลาดเรื่องเดิมซ้ำๆ จนอยากเขียน "อ่านอันนี้ก่อนทำ" ติดไว้
- จะส่ง skill เข้า repo นี้ หรือเปิด GitHub issue เสนอ skill ใหม่ (label `skill-proposal`)
- ไม่แน่ใจว่าสิ่งที่อยากเขียน "ควรเป็น skill หรือแค่ note/SOP" → ใช้ส่วนวินิจฉัยด้านล่าง
- (ยังงงว่าต้องการ skill ตัวไหน ไม่ใช่ "เขียนยังไง") → ไปที่ `what-skill-do-i-need` ก่อน

## วิธีใช้
วาง skill นี้ + เล่าวิจารณญาณที่อยากแพ็ก (เกิดตอนไหน, เลือกยังไง, เคยพลาดยังไง) → AI จะช่วยเช็คว่าควรเป็น skill ไหม, จัดเป็นโครง decision-fork + กับดัก, แล้วร่างตาม format นี้ ให้คุณตรวจ/เติมเคสจริง

---

## ขั้น 1 — นี่ควรเป็น skill ไหม (เช็คก่อนเขียน)
ตอบ "ใช่" ทั้ง 3 ข้อถึงค่อยเขียนเป็น skill:
1. **เกิดซ้ำจริง** — คุณ (หรือทีม) เจอสถานการณ์นี้บ่อยพอที่จะคุ้มเขียนครั้งเดียวใช้ซ้ำ
2. **มีกับดักที่มือใหม่พลาด** — มีจุดที่ "รู้ทฤษฎีแล้วก็ยังพลาด" (ถ้าไม่มีใครเคยพลาด = ไม่ต้องเตือน)
3. **มี "เลือกเมื่อไหร่"** — มี fork ตัดสินใจ (ใช้ A หรือ B / รายงานหรือ reject / เมื่อไหร่ confirm)

ถ้าได้ไม่ครบ 3 → ส่วนใหญ่มันคือ **reference doc / SOP / cheatsheet** ไม่ใช่ skill. (เช่น "ตารางค่าวิกฤต" = reference; "ตัดสินใจยังไงเมื่อเจอค่าวิกฤต" = skill)

## ขั้น 2 — เลือก type ให้ตรงงาน
| type | ใช้เมื่อ | ตัวอย่าง |
|---|---|---|
| **ADVISE** | ช่วยคิด/แนะนำ/วินิจฉัย — ไม่รันอะไรแทน | เลือก test ไหน, อ่านผลแล็บข้ามแขนง, ร่างเอกสาร |
| **DO** | รัน/คำนวณจริง ให้ผลที่เอาไปใช้ตรงๆ | คำนวณ dilution, แปลงหน่วย, นับ workload |
| **CALIBRATION** | เปลี่ยน *วิธี* ที่ AI ทำงาน ไม่ใช่เนื้อหา | บังคับให้ถามกลับก่อนตอบ, โทนการเขียน |

เลือกผิด type = คนใช้คาดหวังผิด. งานคิด/แนะนำ = ADVISE (ค่า default ของสายนี้ส่วนใหญ่).

## ขั้น 3 — ขอบเขต: 1 skill = 1 โดเมนตัดสินใจ
- อย่ายัด "ทุกอย่างเรื่อง Hematology" ลงไฟล์เดียว — ไม่มีใคร route เจอ และยาวจนไม่มีใครอ่าน
- ตัดให้เหลือ **1 ชุดการตัดสินใจที่เกี่ยวกัน** (เช่น "อ่าน CBC flag → review smear มั้ย" แยกจาก "เลือก stat test")
- เกณฑ์ตัด: ถ้าเขียน "## ใช้เมื่อ" แล้ว bullet กระจายไปคนละเรื่อง = ใหญ่เกิน ให้ผ่าเป็น 2 skill

## ขั้น 4 — เขียนเนื้อในแบบ judgment-first
เริ่มจาก **กับดัก #1 + decision-fork หลัก** ไม่ใช่ลอกตำรา. โครงที่ใช้ได้:
1. **กฎข้อ 1 + กับดักข้อ 1** (บนสุด) — สิ่งสำคัญสุดที่อยากให้คนจำได้แม้อ่านแค่ 5 บรรทัด
2. **## ใช้เมื่อ** — เขียนให้เป็น **routing** (คนอ่านต้องรู้ทันทีว่า "เคสฉันใช่อันนี้มั้ย"); ใส่ trigger คำที่คนจะพิมพ์จริง
3. **decision-fork** — ตารางหรือ "ถ้าเจอ X → เลือก Y เพราะ Z"; ใส่ *เพราะอะไร* เสมอ ไม่ใช่แค่ "เลือก Y"
4. **## กับดัก (Anti-patterns)** — ลิสต์ที่มือใหม่พลาดจริง พร้อมวิธีกันแต่ละข้อ
5. **## ช่องสำหรับผู้เชี่ยวชาญเติม** — เว้นที่ให้คนอื่นเติมเคสจากสนามจริง (skill มีชีวิต ไม่ใช่จบที่คุณ)

## ขั้น 5 — generalize + disclaimer ตามความเสี่ยง
- **ลบ PII ทุกชนิด** ก่อนเผยแพร่: ชื่อคนไข้, HN, ชื่อ รพ./สถาบัน, ชื่อเพื่อนร่วมงาน, เคสที่ระบุตัวได้ → แปลงเป็นแบบทั่วไป ("เคสผู้ป่วย anemia", "แล็บแห่งหนึ่ง")
- **disclaimer หนัก/เบาตามความเสี่ยง:**
  - กระทบคนไข้โดยตรง (แปลผล, ตัดสินใจ report) = **หนัก** — ย้ำต้อง verify โดยผู้รู้ + ไม่ใช่คำแนะนำทางการแพทย์
  - แค่จัดไฟล์/สื่อสาร/วางแผนงาน = **เบา** — แต่ยังต้องมี disclaimer ว่าผู้ใช้รับผิดชอบเอง
- ใส่ disclaimer 2 ที่ให้ตรงกัน: ใน frontmatter (`disclaimer:`) และ footer italics ท้ายไฟล์

## ขั้น 6 — ส่งเข้า repo นี้
- อ่าน **CONTRIBUTING.md** ของ repo ก่อน (รูปแบบ frontmatter, การตั้งชื่อไฟล์ kebab-case, การ verify)
- ทางส่ง: เปิด **GitHub issue** เสนอไอเดียก่อน (label `skill-proposal`) แล้วค่อยทำ PR; หรือ PR ตรงถ้าโครงพร้อม
- ในคำเสนอ ระบุ: โดเมนตัดสินใจ 1 ประโยค + กับดัก #1 + ยืนยันว่าลบ PII แล้ว

---

## กับดัก (Anti-patterns)
- **เขียน knowledge แทน judgment** — ใส่นิยาม/สูตร/ตาราง normal range ที่ AI รู้อยู่แล้ว; เก็บไว้แค่เท่าที่จำเป็นต่อการ "เลือก" เท่านั้น
- **skill ครอบจักรวาล** — ใหญ่จนไม่มีใคร route เจอและไม่มีใครอ่านจบ; ผ่าเป็น 1 โดเมน/ไฟล์
- **ลืม "## ใช้เมื่อ" หรือเขียนลอยๆ** — ไม่มีใคร match เคสตัวเองได้ = skill ตายเงียบ; เขียนเป็น routing + trigger คำจริง
- **ทิ้ง PII ไว้** — ชื่อคนไข้/รพ./เคสระบุตัวได้ = ผิดจริยธรรม/กฎหมาย; generalize ทุกครั้งก่อนแชร์
- **disclaimer ไม่ตรงความเสี่ยง** — งานกระทบคนไข้แต่เตือนเบา (อันตราย) หรือจัดไฟล์แต่เตือนหนักจนน่ารำคาญ
- **ลอกโครง skill คนอื่นทั้งดุ้น** — ได้ฟอร์มแต่ไม่มีวิจารณญาณจริงของคุณ = skill เปล่า; ฟอร์มยืมได้ แต่ "เลือกอะไรเมื่อไหร่ + พลาดตรงไหน" ต้องเป็นของจริงจากมือคุณ
- **เขียนจบแล้วล็อก** — ไม่เว้นช่องให้คนเติม; ใส่ "## ช่องสำหรับผู้เชี่ยวชาญเติม" เสมอ

## ช่องสำหรับผู้เชี่ยวชาญเติม
> เติมจากคนที่เคยแพ็กวิจารณญาณตัวเองเป็น skill แล้ว เช่น:
> - *"skill ที่ผมเขียนแล้วคนใช้จริง ต่างจากที่เขียนแล้วเงียบตรงที่..."*
> - *"กับดักที่ผมเคยใส่เป็น knowledge แล้วเพิ่งรู้ว่ามันไม่ใช่ judgment คือ..."*
> - *"วิธี generalize เคสคนไข้โดยไม่เสียแก่นการตัดสินใจ ที่ผมใช้คือ..."*
