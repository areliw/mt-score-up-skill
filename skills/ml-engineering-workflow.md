# นำโมเดล ML ขึ้นใช้จริงให้ไม่พัง

เลือกโมเดลเสร็จแล้ว ทีนี้จะ train→deploy→monitor ยังไงให้ใช้จริงได้นานโดยไม่พังเงียบ — โค้ชนี้ตอบ **"ทำอะไรเมื่อไหร่"** กับ **"พังตรงไหน"** ของงานวิศวกรรมหลังเลือกโมเดล

> **กฎข้อ 1:** ก่อนเริ่ม train จริง ต้องตอบให้ได้ก่อนว่า **"ข้อมูลนี้ reproduce ได้ไหม"** — ล็อก data contract (schema + แหล่งที่เชื่อได้ + เวอร์ชัน) + fix seed + บันทึก env ตั้งแต่รันแรก ไม่ใช่ไปทำตอนพัง · ของที่ reproduce ไม่ได้ = debug ไม่ได้ = ขึ้น production ไม่ได้
> **กับดักข้อ 1:** **offline เก่ง ≠ จริงเก่ง** — คะแนน test สวยแล้ว deploy ตรงเลย คือสูตรพัง. โมเดลพังจริงเพราะ leakage / drift / train-serve skew ที่ offline มองไม่เห็น → ต้องผ่าน shadow/A-B ก่อนเปิดเต็มเสมอ
> "เลือกโมเดล/metric/validation ตัวไหน" ดู `ml-judgment` · "วาง phase ทั้งโปรเจกต์ (business→data→model)" ดู `data-science-workflow` · "งานซ้ำๆ ควรเขียน script แทนคนไหม" ดู `offload-to-automation`

## ใช้เมื่อ
- โมเดลผ่าน offline แล้ว กำลังจะเอาขึ้นใช้จริง (deploy / serve)
- จะวางระบบ train ที่ต้อง "รันซ้ำได้ผลเดิม" + track experiment
- โมเดลที่ใช้อยู่เริ่ม "เพี้ยน" — สงสัย drift / data เปลี่ยน / พังเงียบ
- ต้องตัดสิน serving แบบ batch หรือ realtime + วาง monitor/rollback
- มีคนถาม "รู้ได้ไงว่าโมเดลยังดีอยู่" แล้วตอบได้แค่ "ระบบยังไม่ล่ม"

## วิธีใช้
วาง skill นี้ + เล่าว่าโมเดลทำอะไร · data มาจากไหน · จะ deploy ที่ไหน → AI ชี้ลำดับที่ควรทำ (contract→train→eval→serve→monitor→rollback) + กับดักที่กำลังเสี่ยง ทีละจุด

## ลำดับงาน (AI: ไล่ตามนี้) — อย่าข้ามขั้น

| ขั้น | ต้องล็อกอะไรก่อนไปต่อ | ถ้าข้าม → พังแบบ |
|---|---|---|
| 1. Data contract | schema ตายตัว + แหล่งที่เชื่อได้ + เวอร์ชันข้อมูล | data เปลี่ยนเงียบ โมเดลพังหาเหตุไม่เจอ |
| 2. Reproducible train | fix seed · บันทึก env/lib version · track experiment (param→metric→artifact) | รัน 2 ครั้งได้คนละผล debug ไม่ได้ |
| 3. Eval ค่อยเป็นค่อยไป | offline ผ่าน → shadow → A-B → เปิดเต็ม | deploy ตรง แล้วพังกับคนจริง |
| 4. Serving | เลือก batch vs realtime จาก latency + cost | เลือกผิด → ช้า/แพง/feature ไม่ทัน |
| 5. Monitor 3 ชั้น | data drift + model/quality drift + business metric จริง | เห็นแค่ "ระบบไม่ล่ม" ไม่เห็นโมเดลเสื่อม |
| 6. Rollback + retrain trigger | เกณฑ์ถอย + เกณฑ์ train ใหม่ ตั้งไว้ตั้งแต่แรก | พังแล้วถอยไม่ได้ / ไม่รู้จะ retrain เมื่อไหร่ |

## รายละเอียดจุดที่คนพลาดบ่อย — Decision forks

### Fork 1 — Data contract: ล็อกอะไรก่อน train
- **schema เป็นสัญญา** — กำหนดชนิด/ช่วง/ความหมายแต่ละ field ให้ตายตัว แล้ว validate ขาเข้าทุกครั้ง (ไม่ใช่เชื่อว่า data จะมาเหมือนเดิม)
- **แหล่งที่เชื่อได้ (source of truth)** — รู้ว่า field นี้มาจากตารางไหน/ระบบไหน ใครเป็นเจ้าของ เปลี่ยนแล้วใครบอก
- **เวอร์ชันข้อมูล** — บันทึกว่า "โมเดลตัวนี้ train จาก snapshot ไหน" → ย้อนได้ว่าเกิดอะไรขึ้น
- ⚠️ field ที่ขึ้นกับ "เวลา" (อายุ, ผลที่ออกทีหลัง) = จุดเสี่ยง leakage + drift สูงสุด ดูให้ดี

### Fork 2 — Reproducible training
- **fix seed ทุกจุดสุ่ม** (split, init, shuffle) · ไม่ fix = รัน 2 ครั้งคนละผล เทียบไม่ได้
- **บันทึก environment** — lib version + ค่า config + commit ของ code · "เครื่องผมรันได้" ไม่พอ
- **track experiment** — ทุกการทดลองเก็บ param → metric → artifact คู่กัน เพื่อตอบ "ตัวไหนดีสุด เพราะอะไร" ได้ภายหลัง
- 🎯 เกณฑ์ผ่าน: ลบ workspace แล้ว reproduce โมเดลตัวเดิมจากที่บันทึกไว้ได้ = พร้อมขึ้น production

### Fork 3 — ลำดับ eval: offline → online (ห้ามกระโดด)
- **Offline** (test set ที่ไม่เคยเห็น) = ด่านแรก ผ่านแล้ว *ยังไม่จบ*
- **Shadow** = รันคู่ของจริง แต่ผลโมเดล "ไม่ถูกใช้" → เทียบกับระบบเดิม/ความจริง โดยไม่เสี่ยงคนจริง
- **A-B / canary** = ปล่อยให้ทราฟฟิกส่วนน้อยก่อน วัด business metric จริง แล้วค่อยขยาย
- **เปิดเต็ม** = เมื่อ shadow + A-B ยืนยันแล้วเท่านั้น
- ⚖️ งานกระทบคนไข้/เงิน → shadow ให้นานกว่าปกติ, เกณฑ์ผ่านเข้มกว่าปกติ

### Fork 4 — Serving: batch หรือ realtime
| เลือก | เมื่อ | ระวัง |
|---|---|---|
| **Batch** (รันเป็นรอบ) | ผลไม่ต้องทันที (สรุปรายวัน, จัดคิว, scoring ล่วงหน้า) | ผลเก่าตามเวลา · รอบถัดไปค่อย refresh |
| **Realtime** (ตอบต่อ request) | ต้องผลทันที (กำลังคุยกับ user/เครื่อง) | latency + cost + ต้องมี feature พร้อม ณ เวลานั้น |
- 💡 default = เริ่ม batch ถ้าโจทย์ยอมได้ (ง่าย/ถูก/พังยากกว่า) · realtime เมื่อ "ทันที" คือ requirement จริง

### Fork 5 — Monitor 3 ชั้น (ขาดชั้นไหน = ตาบอดชั้นนั้น)
1. **Data drift** — input เปลี่ยน distribution จากตอน train ไหม (ช่วงค่า/สัดส่วน category/missing เพิ่ม)
2. **Model / quality drift** — เมื่อ ground truth ทยอยมา ผลโมเดลยังแม่นเท่าเดิมไหม (ไม่ใช่แค่ "โมเดลยังตอบ")
3. **Business metric จริง** — ตัวที่โปรเจกต์มีไว้เพื่อ (เช่น คิวเร็วขึ้น/ของเสียลด) ดีขึ้นจริงไหม
- 🚩 monitor แค่ uptime/latency = รู้แค่ "เครื่องยังทำงาน" ไม่รู้ "โมเดลยังถูก" — คนละเรื่องกัน

### Fork 6 — Rollback + retrain (ตั้งเกณฑ์ "ก่อน" พัง)
- **Rollback** — มีเวอร์ชันเก่าพร้อมสลับกลับ + เกณฑ์ชัดว่า "เห็นอะไรถึงถอย" (metric ตกเกินกี่ %, error พุ่ง) ตัดสินใจไว้ล่วงหน้า ไม่ใช่ตอนไฟไหม้
- **Retrain trigger** — นิยามไว้แต่แรกว่า train ใหม่เมื่อไหร่: drift เกิน threshold / quality ตก / ครบรอบเวลา / data ใหม่พอ
- ⚠️ retrain ทุกครั้งต้องวน Fork 1-3 ใหม่ (contract→reproduce→eval ทีละขั้น) ห้ามเอาของใหม่ขึ้นตรง

## กับดัก (Anti-patterns) — พังตรงนี้บ่อย
- **train บน data ที่ผลิตซ้ำไม่ได้** — query สดมือ/snapshot ไม่บันทึก → reproduce/debug ไม่ได้เลย พอพังก็ตามหาเหตุไม่เจอ
- **deploy ตรงไม่มี shadow/A-B** — เชื่อคะแนน offline แล้วเปิดเต็มเลย → พังกับคนจริงทั้งก้อนในครั้งเดียว
- **monitor แค่ "ระบบล่มไหม"** — uptime เขียวแต่โมเดลเดามั่วมาเป็นเดือนโดยไม่มีใครรู้ (ขาด drift + quality + business)
- **ไม่มี rollback** — พบว่าพังแล้วแต่ไม่มีเวอร์ชันเก่าให้ถอย ต้องปล่อยพังต่อระหว่างแก้
- **train/serve skew** — feature ตอน train คำนวณวิธีหนึ่ง ตอน serve อีกวิธี (lib คนละตัว/ลำดับ pre-process ต่าง) → offline สวย จริงเพี้ยน → ใช้ logic แปลง feature ตัวเดียวกันทั้งสองฝั่ง
- **offline เก่งแต่จริงพัง** — เพราะ leakage (ดู `ml-judgment`) / drift (data โลกจริงเปลี่ยน) / ground truth ตอน train ไม่ตรงของจริง → ต้องวัด online ก่อนเชื่อ
- **ไม่ตั้ง retrain trigger** — ปล่อยโมเดลเดิมยาว distribution ค่อยๆ เลื่อนจนเสื่อมแบบไม่มีสัญญาณเตือน

## ช่องสำหรับผู้เชี่ยวชาญเติม
> เติมเคสจริงในสายงานคุณ เช่น:
> - *"(MT/lab) โมเดลที่เราขึ้นใช้... drift ตอน reagent/instrument เปลี่ยน lot จับได้เพราะ monitor ชั้น..."*
> - *"train-serve skew ที่เคยโดน คือ feature ... ตอน serve คำนวณไม่เหมือน train จับได้ตอน..."*
> - *"เกณฑ์ rollback/retrain ที่ทีมเราใช้จริง คือ... เพราะ false-negative มันแพงตรงที่..."*
