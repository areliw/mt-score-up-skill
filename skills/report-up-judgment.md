# สื่อสารขึ้นบน/หัวหน้า-ผู้บริหาร

แปลงเรื่องเทคนิคในแล็บ → สารที่หัวหน้าแล็บ/ผอ.รพ./ฝ่ายบริหาร/คณะกรรมการ "อ่านปุ๊บรู้ปั๊บ" ว่ากระทบอะไรและต้องตัดสินใจอะไร — โดยไม่บิดข้อเท็จจริง

> **กฎข้อ 1:** เริ่มที่ **bottom line ก่อนเสมอ** — บรรทัดแรกต้องตอบ "เกิดอะไร + กระทบใคร(คนไข้/เงิน/เวลา/ความเสี่ยง) + อยากให้ท่านตัดสินใจอะไร". ผู้บริหารอ่านบรรทัดเดียวแล้วได้คำตอบที่ถูก ที่เหลือคือรายละเอียดให้คนอยากเจาะ
> **กับดักข้อ 1:** รายงานแบบเล่ากระบวนการเทคนิคทั้งหมด (run QC, ค่า CV, Westgard rule ตัวไหน fire, troubleshoot ยังไง) = ผู้บริหารหลงและไม่ตัดสินใจ. ผู้รับไม่ได้อยากรู้ "เครื่องพังกลไกไหน" เขาอยากรู้ "ผลออกช้า/คนไข้รอ/ต้องจ่ายเท่าไหร่/ตัดสินใจอะไร". หน้าที่คุณคือ **แปลกลไก → ผลกระทบ** ไม่ใช่ย่อศัพท์เทคนิคให้สั้นลงเฉยๆ

## ใช้เมื่อ
- จะขออนุมัติเครื่อง/น้ำยา/อัตรากำลัง จากหัวหน้าแล็บหรือฝ่ายบริหาร
- ต้องรายงาน QC fail / เครื่องเสีย / ผลออกช้า / NC ขึ้นไปข้างบน
- เสนอปรับ workflow / กระบวนการ ให้ผู้มีอำนาจอนุมัติ
- เขียนสรุปเข้าวาระประชุม / รายงานคณะกรรมการคุณภาพ / บันทึกขออนุมัติ
- มีเรื่องเทคนิคที่ "เขียนกันเองในแล็บรู้เรื่อง" แต่ต้องส่งขึ้นบนให้คนไม่ใช่สาย MT เข้าใจ

## วิธีใช้
วาง skill นี้ + แปะเนื้อเรื่องดิบ (เทคนิค/เหตุการณ์จริง) → บอก *"ผู้รับคือ [หัวหน้าแล็บ/ผอ./กรรมการ] ช่องทางคือ [บันทึก/อีเมล/วาระประชุม/รายงานสั้น]"* → AI จะร่างสารที่ตรงผู้รับ + ขอการตัดสินใจให้ชัด ให้คุณตรวจก่อนส่ง

## เลือกระดับ + ช่องทางตามผู้รับ (ยิ่งสูง ยิ่งสั้น ยิ่งเน้นผลกระทบ)

| ผู้รับ | สนใจอะไรที่สุด | ความยาว/รูปแบบ | สิ่งที่ตัดทิ้งได้ |
|---|---|---|---|
| หัวหน้าแล็บ (สาย MT) | สาเหตุ + แก้ยังไง + ใครทำ | ปานกลาง ศัพท์เทคนิคได้บ้าง | เลขรุ่น/lot ละเอียด (ใส่ตอนถาม) |
| ผอ.รพ. / รองผอ. | คนไข้/บริการ/เงิน/ชื่อเสียง รพ. | สั้น bullet เน้นผลกระทบ | กลไกเครื่อง, Westgard, ค่า CV |
| ฝ่ายบริหาร/การเงิน/จัดซื้อ | คุ้มไหม เสี่ยงไหม จ่ายเท่าไหร่ คืนทุนเมื่อไหร่ | สั้น ตัวเลขเด่น | ศัพท์แล็บทั้งหมด |
| คณะกรรมการคุณภาพ/วาระประชุม | NC คืออะไร แก้ไข+ป้องกันยังไง สถานะ | มีโครง: ปัญหา→ผลกระทบ→แก้ไข→ป้องกัน→ขออนุมัติ | play-by-play การ troubleshoot |

## สิ่งที่ "เก็บไว้ / ตัดทิ้ง / แปล" (หัวใจของการ report up)
- **เก็บไว้** — ชื่อเครื่อง/รุ่น, ชื่อ test/รายการ, เลขเอกสาร NC/CAPA, lot/รหัสที่ใช้ track, ตัวเลขผลกระทบ (จำนวนคนไข้, บาท, ชั่วโมง/วันที่ล่าช้า). พวกนี้คือสะพานให้ผู้บริหาร track ต่อ
- **ตัดทิ้ง** — ขั้นตอน troubleshoot ทีละสเต็ป, ค่า CV/SD ดิบ, Westgard rule ตัวไหน fire, ชื่อ reagent ย่อยๆ, จอ error code. ไม่ actionable กับผู้รับ
- **แปล** — กลไก → ผลกระทบเป็นภาษาคน 1-2 ประโยค **โดยไม่โกหก**: ไม่ใช่ *"Levey-Jennings ละเมิด 1-3s + 2-2s"* แต่ *"ค่าควบคุมคุณภาพหลุดเกณฑ์ ทำให้ปล่อยผลกลุ่มนี้ไม่ได้จนกว่าจะแก้ คนไข้รอผลเพิ่มราว 2 ชม."* — QC fail ยังเป็น QC fail, อย่าลดเป็น "เครื่องมีปัญหานิดหน่อย"
- **อย่า over-strip** — หัวหน้าแล็บอ่านศัพท์ระดับแนวคิดออก (QC, calibration, TAT, contamination, carryover, lot, reflex test). เส้นแบ่งคือ *"แนวคิดนี้มีอยู่จริงและสำคัญกับเรื่องนี้"* (เก็บ) กับ *"นี่คือฟังก์ชัน/lot/error code/ค่าดิบ"* (ตัด). แทน "QC fail" ด้วย "เครื่องงอน" = ดูถูกคนอ่าน

## เลือกความยาว/รูปแบบตามช่องทาง (เนื้อเดิม เปลือกต่าง)
- **บันทึกขออนุมัติ / รายงานคณะกรรมการ** — มีโครงเต็ม หัวข้อตัวหนา สแกนง่าย: สรุป(TL;DR) → ผลกระทบ → สาเหตุย่อ → ผู้รับผิดชอบ → สิ่งที่ขอตัดสินใจ. เรียงตามสิ่งที่สำคัญสุดของเรื่องนี้
- **อีเมลถึงผู้บริหาร** — หัวเรื่อง = TL;DR แบบวลีนาม (เห็นแล้วรู้เรื่อง), เนื้อ 2-3 ย่อหน้า ไม่ต้องหัวข้อตัวหนา, ปิดท้ายด้วยจุดที่ต้องการการตัดสินใจ
- **LINE กลุ่ม/แชตด่วน** — บรรทัดแรก = bottom line, ใต้นั้น 2-3 bullet (ผลกระทบ/ใครคุม/ขออะไร), ไม่ต้องทักทาย-ลงท้าย, ลิงก์/เลขเอกสารฝังในประโยค
- **วาจาในที่ประชุม** — bullet สั้นๆ คลอสเดียวต่อบรรทัด เรียงตามลำดับที่จะพูด, ใส่ตัวเลข/เลขเอกสารที่จะอ้างไว้ในบรรทัดนั้นกันลืม
> ยิ่งช่องทางเร็ว/ผู้รับสูง → ยิ่งสั้น และยิ่งต้องเอา bottom line + ผลกระทบขึ้นก่อน. อย่าก๊อปบันทึกยาวไปแปะ LINE

## VERDICT — ตัวอย่างแปลง (เทคนิค → ขึ้นบน)
- **ขออนุมัติเครื่อง/น้ำยา:** ❌ "เครื่องเดิม throughput ต่ำ rerun เยอะ" → ✅ *"เครื่องปัจจุบันทำให้ผลออกช้าเฉลี่ย X ชม. คนไข้ตกค้าง Y ราย/วัน — ขออนุมัติงบ Z บาท คืนทุนใน N เดือนจากค่าล่วงเวลา+น้ำยาที่เสียซ้ำที่ลดได้"*
- **รายงาน QC fail:** ❌ "2-2s across 2 levels, recalibrate แล้ว" → ✅ *"พบค่าควบคุมหลุดเกณฑ์รายการ [test] เช้านี้ — กลั้นผลไว้ ยังไม่กระทบคนไข้ ทีมแก้แล้ว คาดปล่อยผลได้ภายใน [เวลา] · รายงานเพื่อทราบ ไม่ต้องตัดสินใจ"*
- **เสนอปรับ workflow:** ❌ "ย้ายขั้น centrifuge มาก่อน aliquot ลด TAT" → ✅ *"ปรับลำดับงานช่วยให้ผลด่วนถึงมือแพทย์เร็วขึ้น ~X นาที ไม่ใช้งบเพิ่ม — ขออนุมัติทดลอง 2 สัปดาห์แล้ววัดผล"*
- **ขออัตรากำลัง:** ❌ "คนไม่พอ overtime เยอะ" → ✅ *"ปริมาณงานโตขึ้น [X]% ใน [ช่วงเวลา] ทำให้ค่าล่วงเวลา [฿]/เดือน และเสี่ยงผลพลาดจากความล้า — ขออนุมัติอัตรา [N] ตำแหน่ง คุ้มกว่าค่า OT ใน [N] เดือน"*
- **เครื่องเสียกะทันหัน:** ❌ "เครื่อง down รอช่าง" → ✅ *"เครื่อง [รุ่น] ใช้งานไม่ได้ตั้งแต่ [เวลา] — รายการ [test] หยุดชั่วคราว, ส่งงานด่วนไปเครื่องสำรอง/รพ.ข้างเคียงแล้ว, ช่างมา [เวลา] · รายงานเพื่อทราบ จะอัปเดตเมื่อกลับมาปกติ"*

## ตัวอย่างเต็ม — บันทึกขออนุมัติเครื่อง (โครงที่ผ่านง่าย)
> **สรุป:** ขออนุมัติจัดซื้อเครื่อง [รุ่น] ทดแทนเครื่องเดิมที่ทำให้ผลออกช้าและคนไข้ตกค้าง — งบ [Z] บาท คาดคืนทุน [N] เดือน
> **ผลกระทบตอนนี้:** เครื่องเดิมทำผลล่าช้าเฉลี่ย [X] ชม./วัน คนไข้รอผลเพิ่ม [Y] ราย/วัน, มีค่าล่วงเวลาทีม [฿] /เดือน เพื่อตามงานให้ทัน
> **สาเหตุย่อ:** เครื่องอายุเกินอายุใช้งาน อะไหล่เลิกผลิต ซ่อมแล้วเสียซ้ำ — ไม่ใช่ปัญหาวิธีทำงานของทีม
> **สิ่งที่ขอ:** อนุมัติ ตัวเลือก A (ซื้อ [฿]) หรือ B (เช่า/lease [฿]/เดือน) ภายใน [วันที่] เพื่อทันรอบงบประมาณ
> **ความเสี่ยงถ้าไม่ทำ:** ถ้าเครื่องเดิมเสียถาวร ต้องส่งตัวอย่างออกนอก รพ. คนไข้รอผลข้ามวัน
>
> สังเกต: ทุกบรรทัดวัดเป็น **คนไข้/บาท/เวลา/ความเสี่ยง** ไม่มีคำว่า throughput, CV, rerun, error code.
> ผู้รับอ่านบรรทัด "สรุป" บรรทัดเดียวก็ตัดสินใจได้ ที่เหลือคือหลักฐานให้คนอยากเจาะ.
> ตัวเลขในวงเล็บ [ ] = ต้องเติมของจริงที่ verify แล้ว ห้ามปล่อยลอยหรือเดา.

## ขอการตัดสินใจให้ชัด (อย่าจบลอย)
ทุกสารที่ส่งขึ้นต้องระบุ **1 อย่าง** ให้ชัดว่าผู้รับต้องทำอะไร:
- **เพื่อทราบ** (ไม่ต้องทำอะไร) — บอกตรงๆ ว่า "รายงานเพื่อทราบ"
- **ขออนุมัติ** — บอกตัวเลือก + ตัวเลข + เส้นตาย ("ขออนุมัติ A หรือ B ภายในวันที่ ___")
- **ขอตัดสินใจ/สั่งการ** — วางทางเลือกพร้อมข้อดี-เสีย ให้เขาเลือก ไม่ใช่ให้เขาไปคิดเอง
> ให้ข้อเท็จจริง+ทางเลือก แต่ **อย่าสั่งผู้บริหารว่าต้องทำอะไร** ("ท่านควรรีบอนุมัติ" = เสียมารยาท). เสนอเป็นทางเลือก เขาตัดสินใจ

## Escalate เรื่อง NC / ความเสี่ยง / ความปลอดภัย
- ⛔ เรื่องกระทบคนไข้/ความปลอดภัย/ค่าวิกฤต/ปล่อยผลผิด: **รายงานทันที + ตรงไปตรงมา ห้ามทำให้ดูเบาลงเพื่อความสวยงาม**. "อาจมีผลที่รายงานผิดออกไปแล้ว N ราย" ห้ามแปลงเป็น "อาจมีข้อสังเกตเล็กน้อย"
- ระบุให้ครบ: เกิดอะไร → กระทบใคร/กี่ราย → ตอนนี้คุมไว้ยังไง → ต้องการให้ผู้รับทำอะไร/ตัดสินใจอะไร
- ความสุภาพ = ที่ **น้ำเสียง** เท่านั้น ไม่ใช่ที่ความเด็ดขาดของการแจ้งเตือน (ดู `polite-but-clear`)
- รายงานช่องทางที่ไวที่สุดก่อน (โทร/LINE หัวหน้า) แล้วค่อยตามด้วยบันทึกเป็นลายลักษณ์อักษร — อย่ารอเขียนบันทึกสวยๆ ก่อนค่อยแจ้ง

## เช็คก่อนส่ง (อ่านในมุมผู้รับ)
1. อ่านบรรทัดแรกบรรทัดเดียว — **ผู้รับรู้ไหมว่าต้องตัดสินใจอะไร/แค่รับทราบ?**
2. ตัวเลข/ชื่อเครื่อง/เลขเอกสารทุกตัว — **verify แล้วหรือยัง?** (ห้ามเดา ห้าม mental-math)
3. มีศัพท์เทคนิคที่ผู้รับระดับนี้ไม่จำเป็นต้องรู้หลงเหลือไหม → แปลเป็นผลกระทบ
4. มีจุดที่เผลอ "สั่ง" ผู้บริหารไหม → เปลี่ยนเป็นเสนอทางเลือก
5. timing — เป็นจังหวะที่ผู้รับพร้อมพิจารณาไหม (ไม่ใช่ตอนวิกฤต/หลังปิดรอบงบ)? เรื่องขอเงินต้องส่งทันรอบงบประมาณ

## กับดัก (Anti-patterns)
- **เล่ากระบวนการเทคนิคแทนผลกระทบ** — ผู้บริหารไม่อยากรู้ว่าแก้ยังไง อยากรู้ว่ากระทบอะไร+ต้องทำอะไร
- **ฝัง bottom line ไว้ท้ายสุด** — เขาอ่านไม่ถึง; เอาคำตอบขึ้นบรรทัดแรกเสมอ
- **ย่อศัพท์เทคนิคแต่ไม่แปลเป็นผลกระทบ** — "ลด TAT" สั้นแต่ยังไม่ใช่ภาษาผู้บริหาร; ต้อง "คนไข้ได้ผลเร็วขึ้น X นาที"
- **over-strip จนดูถูกผู้รับ** — หัวหน้าแล็บอ่านศัพท์ MT ออก; เปลี่ยน "QC fail" เป็น "เครื่องงอน" = ดูถูก. ตัด *ชื่อฟังก์ชัน/lot/error code* พอ ไม่ใช่ตัดศัพท์ระดับแนวคิด
- **จบลอยไม่ขอการตัดสินใจ** — รายงานแล้วผู้รับไม่รู้ว่าต้องอนุมัติ/สั่ง/แค่รับทราบ
- **ปั้นความเสี่ยง/แต่งตัวเลขให้ดูขยัน** — ความเสี่ยงจริงเท่านั้น; ตัวเลขทุกตัวต้อง verify ก่อน อย่าเดา
- **ทำเรื่อง NC/ความปลอดภัยให้ดูเบาลง** — เพื่อความสวยงามของรายงาน = อันตรายที่สุด
- **เขียนยาวเกินช่องทาง** — ก๊อปบันทึก 1 หน้าไปแปะ LINE หรือพูดยาวในประชุม; เลือกความยาวตามช่องทาง+ผู้รับ
- **hedge จนไม่เป็นข้อมูล** ("น่าจะ", "อาจจะ", "ดูเหมือนว่า") — ถ้ารู้ก็บอก ถ้าไม่รู้บอกว่า "ยังหาสาเหตุไม่เจอ" ตรงๆ ดีกว่าคลุมเครือ
- **เล่ากระบวนการ debug ทั้งหมด** — ผู้บริหารสนใจว่า "เจอแล้ว/แก้แล้ว" ไม่ใช่ว่าไล่เช็คอะไรไปบ้างทีละขั้น
- **ข้ามหัวหน้าไปหา level บนพร่ำเพรื่อย** — skip-level บ่อยๆ ทำลายความไว้ใจ; ส่งตามสายเว้นแต่เป็นเรื่องความปลอดภัย/จริยธรรมที่สายตรงนิ่ง

## ช่องสำหรับผู้เชี่ยวชาญเติม
> เติมเคสจริงในสายงานคุณ เช่น:
> - *"(MT) บันทึกขออนุมัติน้ำยา/เครื่องที่ผ่านฉลุย ผมเขียน bottom line ว่า..."*
> - *"ตอนรายงาน QC fail/NC ขึ้น ผอ. ประโยคที่ทำให้ไม่ตื่นตระหนกแต่เข้าใจคือ..."*
> - *"ตัวเลขผลกระทบที่ผู้บริหารตอบสนองไวสุด (คนไข้รอ/บาท/วันล่าช้า) คือ..."*

*ช่วยเรียบเรียงการสื่อสารขึ้นบน ไม่ใช่คำแนะนำทางการแพทย์ — ข้อเท็จจริง/ตัวเลขที่รายงานต้อง verify ก่อน ผู้นำไปใช้รับผิดชอบการสื่อสารที่นำไปใช้จริง · ผู้สร้างไม่รับผิดต่อความเสียหายจากการนำไปใช้ · ดูคู่กับ `polite-but-clear` และ `lab-management-judgment`*
