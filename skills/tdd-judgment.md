# เขียนเทสต์ให้คุ้ม + TDD

เขียนสคริปต์คำนวณ/parse ผลแล็บแล้วไม่แน่ใจว่า "ต้องเทสต์อะไร เทสต์ตอนไหน" → skill นี้ช่วย **เลือกว่าอันไหนคุ้มเทสต์ + จับเทสต์ที่ผ่านแต่ไม่จับบั๊ก** ไม่ใช่สอน syntax pytest.

> **กฎข้อ 1:** เทสต์ **พฤติกรรม (ผลที่ฟังก์ชันให้)** ไม่ใช่ **วิธีข้างใน**. เทสต์ที่ดีอ่านเหมือนสเปก — "ใส่ Hb 7.2 + MCV 65 → flag เป็น microcytic anemia" บอกว่าระบบทำอะไรได้ ไม่สนว่าเขียน if/loop ยังไง → แก้โค้ดข้างในแล้วเทสต์ยังเขียว. ถ้าเปลี่ยนชื่อฟังก์ชันภายในแล้วเทสต์แดง = คุณเทสต์ "วิธี" ไม่ใช่ "ผล" → เทสต์เปราะ.
> **กับดักข้อ 1:** เทสต์ "เขียว" ≠ โค้ดถูก. เทสต์ที่เช็คแค่ "ไม่ error / รูปร่าง output ใช่" จะผ่านทั้งที่ค่าผิด. เทสต์ต้องมี **ค่าที่รู้คำตอบแน่ (known-answer)** ที่จะ **แดงถ้าตรรกะพัง** — ถ้าลบโค้ดคำนวณทิ้งแล้วเทสต์ยังเขียว = เทสต์นั้นไร้ค่า.

## ใช้เมื่อ
- เขียนสคริปต์คำนวณ/แปลงผลแล็บ (เช่น คำนวณ index, parse ค่าจาก CSV เครื่อง, แปลงหน่วย, จัด flag critical value)
- จะตัดสินใจว่า "ฟังก์ชันไหนคุ้มเทสต์ก่อน" เมื่อเวลาจำกัด
- โค้ดเคยพังเงียบๆ / ผลเพี้ยนแล้วไม่รู้ตัว อยากกันไม่ให้พังซ้ำ
- ลังเลว่าต้อง mock/fixture ไหม, coverage เท่าไรพอ
- แก้บั๊กแล้วอยากกันมันกลับมา (regression)

## วิธีใช้
วาง skill นี้ + วางโค้ด/อธิบายฟังก์ชันที่จะเทสต์ → AI ช่วยจัดลำดับว่าอันไหนคุ้มเทสต์ก่อน, ร่างเคส known-answer + edge case, และชี้ว่าเทสต์ที่มีอยู่ "จับบั๊กจริงไหม". ถ้า AI รันโค้ดได้ ให้มันรันวงรอบ red→green ให้ดู.

## TDD: วงรอบ red-green-refactor (ทำทีละชั้น อย่ารวด)

| ขั้น | ทำอะไร | กฎเหล็ก |
|---|---|---|
| 🔴 RED | เขียนเทสต์ 1 อันสำหรับพฤติกรรม 1 อย่าง → ต้อง **แดงก่อน** | ถ้าเทสต์เขียวทั้งที่ยังไม่เขียนโค้ด = เทสต์ผิด |
| 🟢 GREEN | เขียนโค้ด **น้อยสุด** ให้ผ่านเทสต์นั้น | อย่าเขียนเผื่ออนาคต |
| ♻️ REFACTOR | จัดโค้ดให้สะอาดโดยเทสต์ยังเขียว | **ห้าม refactor ตอนแดง** — เขียวก่อน |

**กับดักใหญ่ — horizontal slicing:** เขียนเทสต์ทั้งหมดทีเดียวก่อน แล้วค่อยเขียนโค้ดทั้งหมด = ได้เทสต์ห่วย เพราะเทสต์ "พฤติกรรมที่จินตนาการ" ไม่ใช่ของจริง. ทำ **vertical: 1 เทสต์ → 1 โค้ด → วนใหม่** เทสต์ถัดไปเรียนจากรอบที่แล้ว.

## เทสต์ TDD เต็มรูปคุ้มเมื่อไหร่ — VERDICT

| สถานการณ์ | คุ้มทำ TDD เต็ม? | เพราะ |
|---|---|---|
| ฟังก์ชันคำนวณ/parse ที่ "ผลถูกผิดสำคัญ" (index, flag, แปลงหน่วย) | ✅ คุ้มสุด | เป็น core logic ที่พังแล้วผลแล็บเพี้ยน |
| pipeline/feature engineering ก่อนเข้าโมเดล | ✅ คุ้ม | data leakage/แปลงผิด = เทสต์จับได้ |
| แก้บั๊ก | ✅ เขียนเทสต์ repro ที่ "แดง" ก่อนแก้ | กันบั๊กกลับมา (regression) |
| สคริปต์ explore/วิเคราะห์ครั้งเดียวทิ้ง | ❌ ข้ามได้ | เขียนเทสต์แพงกว่าตรวจตาเอง |
| โค้ด glue / โยน I/O เฉยๆ | ⚠️ เทสต์เฉพาะส่วนที่มี logic | ส่วนที่แค่ต่อท่อ ไม่ต้องเทสต์ |
| loop เทรนโมเดล ML | ❌ TDD ไม่เข้า | feedback คนละแบบ — วัดด้วย metric ไม่ใช่ assert |

## เทสต์อะไรก่อน + mock/fixture เมื่อไหร่ (Judgment)

- **ลำดับเทสต์:** เริ่มที่ **happy path ค่าที่รู้คำตอบ** 1 เคส (tracer bullet) → แล้วค่อย **edge ที่กัดจริง**: ค่าว่าง/None, ค่าติดลบ/0, ขอบ reference range, หน่วยผิด, แถวพังใน CSV, ค่า critical. อย่าไล่เทสต์ทุก permutation — เน้นเส้นทางที่พังแล้วเจ็บ.
- **fixture เมื่อไหร่:** มี setup ซ้ำหลายเทสต์ (ตัวอย่าง dataframe ผลแล็บ, ไฟล์ตัวอย่าง) → ทำเป็น fixture. ไฟล์ชั่วคราวใช้ `tmp_path` ให้ลบเองอัตโนมัติ อย่าเขียนไฟล์จริงค้างไว้.
- **parametrize เมื่อไหร่:** ตรรกะเดียว input หลายชุด (ช่วงค่าหลายแบบ → flag คาดหวัง) → 1 เทสต์ parametrize ดีกว่า copy 6 เทสต์.
- **mock เมื่อไหร่:** mock เฉพาะ **ของนอกที่ควบคุมไม่ได้** (API เครื่อง LIS, DB, เวลา/`now()`, ไฟล์เครือข่าย). **อย่า mock ตรรกะของตัวเอง** — mock เยอะ = เทสต์ผ่านแต่ของจริงพัง.
- **coverage เป็นเครื่องมือ ไม่ใช่เป้า:** 80% บอกว่า "บรรทัดไหนไม่เคยถูกรัน" = ช่องโหว่. แต่ 100% ไม่ได้แปลว่าถูก — รันผ่านได้โดยไม่ assert อะไรเลย. ใช้ coverage หา **โค้ดที่ลืมเทสต์** ไม่ใช่ไล่ตัวเลขให้สวย.

## กับดัก (Anti-patterns) — เช็คก่อนเชื่อว่า "เทสต์ผ่านแล้วชัวร์"
- **เทสต์ที่ไม่มี assert จริง** — เช็คแค่ "รันไม่ error" หรือ `assert result is not None` → ผ่านทั้งที่ค่าผิด. ต้อง assert **ค่าที่รู้คำตอบแน่**.
- **เทสต์ผูกกับวิธีข้างใน** — mock ฟังก์ชันภายใน/เช็คว่าเรียกกี่ครั้ง → แก้โค้ดให้ดีขึ้นแล้วเทสต์แดงทั้งที่ผลถูก = เทสต์เปราะ ทิ้งได้.
- **horizontal slicing** — เขียนเทสต์รวดทั้งชุดก่อนเขียนโค้ด → เทสต์ "รูปร่าง" ไม่ใช่พฤติกรรม จับบั๊กไม่ได้.
- **เทสต์ที่ลอกค่าจาก output ปัจจุบันมาเป็น expected** — ถ้าโค้ดผิดอยู่ คุณกำลัง "ล็อกความผิด". expected ต้องมาจากคำนวณมือ/อ้างอิงภายนอก.
- **เทสต์แชร์ state กัน** — เทสต์ A ทิ้งไฟล์/แก้ตัวแปร global ให้ B → ผ่าน/แดงสลับตามลำดับรัน. ทุกเทสต์ต้องอิสระ (ดู `python-coach`: mutable default, copy vs reference).
- **mock จนไม่เหลือของจริง** — mock ทั้ง pipeline → เทสต์เขียว 100% แต่ integration พังหมด.
- **ไล่ coverage เป็นเป้า** — เติมเทสต์ขยะให้ถึง 90% แทนที่จะเทสต์ critical path ให้ลึก.
- **float เทียบตรงๆ ในเทสต์** — `assert calc() == 0.3` แตกเพราะ float ไม่แม่น → ใช้ `pytest.approx`/`math.isclose` (ดู `python-coach`).
- **refactor ตอนเทสต์ยังแดง** — แยกไม่ออกว่าพังเพราะ refactor หรือเพราะ logic เดิม.

## ช่องสำหรับผู้เชี่ยวชาญเติม
> เติมเคสจริงในสายงานคุณ เช่น:
> - *"(MT) ฟังก์ชัน parse ผลจากเครื่อง X ที่ผมเคยพังเงียบ คือ... เทสต์ที่ควรมีคือ..."*
> - *"ตอนทำ pipeline ข้อมูลแล็บ ผมเคยเจอ data leakage เพราะ... เทสต์จับด้วย..."*
> - *"edge case ผลแล็บที่ลืมเทสต์บ่อยสุด คือ... (เช่น hemolyzed flag, ค่า <LOD, หน่วยปน)"*

> งานที่ "ควรปล่อยให้ออโต้รันเทสต์ทุกครั้งที่แก้โค้ด" → ดู `offload-to-automation`. เลือก data structure/จับบั๊ก Python → ดู `python-coach`.
