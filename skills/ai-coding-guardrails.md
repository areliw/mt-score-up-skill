# กันกับดักตอนให้ AI เขียนโค้ด

คุณไม่ต้องเขียนโค้ดเป็นก็คุม AI ได้ — skill นี้ให้ "กฎสั่งงาน" ที่กันไม่ให้ AI เขียนเกินจำเป็น เดาเงียบๆ หรือรื้อของที่ใช้อยู่จนพัง

> **กฎข้อ 1:** บอกขอบเขตให้ **แคบที่สุด** ก่อนสั่ง — "แก้เฉพาะฟังก์ชันนี้ ไฟล์นี้ ห้ามแตะส่วนอื่น" + บอกว่า "เสร็จแล้วต้องเช็คยังไงถึงรู้ว่าถูก" (success ที่ตรวจได้). งานกว้างลอย ("ทำให้มันทำงาน") = AI เดาเอง แล้วคุณไล่แก้ไม่จบ.
> **กับดักข้อ 1:** โค้ดยาว/ฉลาดดู ≠ โค้ดดี. AI ชอบ over-engineer (เผื่ออนาคต เพิ่ม option ที่ไม่ได้ขอ จับ error ที่ไม่มีวันเกิด) ทำให้ของง่ายๆ กลายเป็นซับซ้อนจน **คุณอ่านไม่ออก = ตรวจไม่ได้ = ไว้ใจไม่ได้**. โค้ดที่คุณเข้าใจ 50 บรรทัด > โค้ดเทพ 200 บรรทัดที่คุณงง.

## ใช้เมื่อ
- ให้ AI ช่วยเขียน/แก้สคริปต์วิเคราะห์หรือ parse ผลแล็บ (เช่น อ่าน CSV จาก LIS, นับ/สรุปผล, ทำกราฟ QC)
- จะ "accept" โค้ดที่ AI เขียนมาทั้งก้อนทั้งที่ยังไม่เข้าใจมันทำอะไร
- งานแก้ของเดิมที่ใช้อยู่ (กลัว AI รื้อจนของที่เคยรันได้พัง)
- AI เขียนยาวเกิน/ซับซ้อนเกิน หรือเปลี่ยนของที่ไม่ได้ขอให้เปลี่ยน
- สั่งไปแล้วได้ผลคนละทางทุกรอบ เพราะไม่เคยบอกว่า "ถูก" หน้าตาเป็นยังไง

## วิธีใช้
วาง skill นี้ + บอกงานที่อยากให้ AI ทำ (แปะโค้ด/ไฟล์ตัวอย่างผลแล็บถ้ามี) → ใช้ "ลำดับสั่งงาน" ข้างล่างคุม AI ทีละชั้น แล้วตรวจตามเช็กลิสต์ก่อน accept ทุกครั้ง

---

## ลำดับสั่งงาน (Judgment — ทีละชั้น อย่ารวด)
แต่ละชั้น = สั่งแบบไหน → กันอะไร:
1. **เป้า + เกณฑ์ถูก:** "อ่านไฟล์ CBC → flag ค่าเกิน reference → เซฟไฟล์ใหม่" + ตัวอย่าง 1 แถวที่ถูก → กันผลแกว่งทุกรอบเพราะ "ดี" ไม่ชัด
2. **เผยสมมติฐานก่อนลงมือ:** "ไม่ชัดให้ถามกลับ 1-3 ข้อ อย่าเดา" — ชื่อคอลัมน์? ตัวคั่น (`,`/`;`)? encoding ไทย? ค่าหายทำไง → กัน AI เดาเงียบแล้วผล "ดูปกติ" แต่ผิด
3. **surgical edit:** "แก้เท่าที่จำเป็น คงสไตล์เดิม ห้ามจัดรูปแบบ/เปลี่ยนชื่อตัวแปรอื่น เจอโค้ดตายให้บอก อย่าลบเอง" → กัน AI รื้อโค้ดข้างเคียงที่รันได้อยู่จนพัง
4. **เวอร์ชันเล็กสุดก่อน:** "ทำตัวใช้ได้ก่อน ค่อยเพิ่มถ้าจำเป็น ไม่ต้องเผื่ออนาคต/เพิ่ม option" → กันโค้ดบวมจนอ่านไม่ออก
5. **อธิบาย + ทดสอบเอง:** "อธิบายเป็นภาษาคนทีละขั้น + รันกับตัวอย่างนี้แล้วโชว์ผล" → กันคุณ accept ของที่ไม่เข้าใจ
6. **พอแล้วหยุด:** ผลถูกแล้ว อย่าสั่ง "ปรับให้ดีขึ้นอีก" ลอยๆ → มักพังของที่ดีอยู่แล้ว

**อย่ารันคำสั่งที่ไม่เข้าใจ โดยเฉพาะที่ลบ/เขียนทับ** (`rm`, `del`, overwrite, `DROP`, format) — ให้ AI อธิบายก่อนว่าแตะ/ลบ/ทับไฟล์อะไร แล้วลองกับสำเนา/ข้อมูลทดสอบก่อนเสมอ

## VERDICT — อ่าน+เข้าใจก่อน accept

> **ก่อนเริ่ม: เลือกระดับตามความเสี่ยง — "อ่านทุกบรรทัด" ใช้ไม่ได้กับงานใหญ่**
> เช็กลิสต์ข้างล่างออกแบบมาสำหรับสคริปต์สั้น (หลักสิบ-ร้อยบรรทัด) พอโค้ดโตเป็นหลักพันบรรทัดหรือหลายไฟล์ การบังคับ "อ่านให้เข้าใจทุกบรรทัดก่อน accept" จะกลายเป็นพิธีกรรม — อ่านไม่ไหวจริง สุดท้ายกด accept ทั้งที่ไม่ได้อ่าน = แย่กว่าไม่มีกฎ
> - **เสี่ยงต่ำ** (สคริปต์ใช้ครั้งเดียว ไม่แตะข้อมูลจริง): เช็กลิสต์ข้างล่างพอ
> - **เสี่ยงกลาง** (รันซ้ำ/แตะไฟล์จริง): เช็กลิสต์ + **behavioral oracle** — เขียนเคสที่*รู้คำตอบอยู่แล้ว* แล้วให้โค้ดตอบ ถูกทุกเคสจึงผ่าน
> - **เสี่ยงสูง** (เขียนทับ/ลบ/ส่งออก/ตัวเลขที่เอาไปตัดสินใจ): oracle + **negative control** (ใส่ input ที่*ต้องทำให้พัง* ถ้าไม่พัง = แปลว่าไม่ได้ตรวจจริง) + ให้คนอื่นหรือ AI อีกตัวรีวิวแยก
>
> ⚠️ ตัวเลขทุกตัว (coverage %, จำนวนเทสต์ที่ผ่าน, lint เขียว) เป็น **ตัวแทน ไม่ใช่ความถูกต้อง** — exit 0 ไม่ได้แปลว่าโค้ดทำงานถูก ดูกับดัก "เชื่อ metric แทนผลจริง" ด้านล่าง

ถ้าตอบ "ไม่" ข้อใดข้อหนึ่ง = **ยังไม่ accept** ให้ถาม AI ต่อจนเข้าใจ:
- เข้าใจไหมว่าโค้ดนี้รับ input อะไร คืน output อะไร?
- ลองรันกับข้อมูลจริง 1 ชุดแล้วผลถูกไหม? (อย่าเชื่อแค่ AI บอกว่า "ใช้ได้")
- มันแตะเฉพาะที่ขอ หรือไปเปลี่ยนอย่างอื่นด้วย? (เทียบ diff/ของเดิม)
- ถ้า input เพี้ยน (ไฟล์ว่าง/คอลัมน์ขาด/ค่าว่าง) มันพังเงียบหรือเตือน?
- backup ข้อมูลจริงไว้ก่อนรันหรือยัง? (โค้ด AI ที่เขียน/ลบไฟล์ พังครั้งเดียวกู้ไม่ได้ถ้าไม่มีสำเนา)

## เทคนิคที่คุ้ม (ใช้ตอนจำเป็น)
- **"ทำเป็นขั้น แล้วหยุดให้ผมเช็กแต่ละขั้น"** — งานยาว/หลายไฟล์ กันหลุดยกแผง
- **"ร่าง 2 แบบ: ง่ายสุด / ครบสุด"** — แล้วเลือก เร็วกว่าไล่แก้ทีละรอบ
- **โยน edge case จริงให้ลอง** — ไฟล์แล็บที่มี header แปลกๆ / ภาษาไทย / ค่าว่าง ก่อนเชื่อว่าโค้ดทน

## ทางแยก (เลือกอะไรเมื่อไร)
> ลำดับสั่งงาน + VERDICT ข้างบนคือวิธีทำ — ตารางนี้รวมจุดที่ต้อง **เลือก** ไว้ที่เดียว (ทุกแถวมาจากส่วนข้างบนของการ์ดนี้)

| ทางแยก | ถ้า... | เลือก | เพราะ |
|---|---|---|---|
| **ตรวจลึกแค่ไหน** (VERDICT) | สคริปต์ใช้ครั้งเดียว ไม่แตะข้อมูลจริง | เช็กลิสต์ 5 ข้อ | พอกับความเสี่ยง |
| | รันซ้ำ / แตะไฟล์จริง | เช็กลิสต์ + behavioral oracle (เคสที่รู้คำตอบ) | "ดูปกติแต่ผิด" จับได้ด้วยเคสที่รู้คำตอบเท่านั้น |
| | เขียนทับ / ลบ / ส่งออก / ตัวเลขที่ใช้ตัดสินใจ | oracle + negative control + รีวิวแยก | "อ่านทุกบรรทัด" ใช้ไม่ได้กับงานใหญ่ = พิธีกรรม |
| **แก้ของเดิม vs เขียนใหม่** | มีโค้ดที่รันได้อยู่แล้ว | surgical edit (ชั้น 3) | กันรื้อของที่ใช้ได้จนพัง |
| | ยังไม่มีอะไรเลย | เวอร์ชันเล็กสุดก่อน (ชั้น 4) | กันโค้ดบวมจนอ่านไม่ออก |
| **AI ถามกลับ vs ลงมือ** (ชั้น 2) | ชื่อคอลัมน์ / ตัวคั่น / encoding ไทย / ค่าว่าง ยังไม่ชัด | ให้ถามกลับ 1-3 ข้อก่อน | เดาเงียบ = ผลดูปกติแต่ผิด |
| **accept / ถามต่อ / หยุด** | ตอบ "ไม่" ข้อใดในเช็กลิสต์ | ยังไม่ accept — ถามต่อจนเข้าใจ | ตรวจไม่ได้ = ไว้ใจไม่ได้ |
| | ผลถูกตามเกณฑ์ที่ตั้งไว้แล้ว | หยุด (ชั้น 6) อย่าสั่ง "ปรับให้ดีขึ้นอีก" ลอยๆ | มักพังของที่ดีอยู่แล้ว |
| **คำสั่งลบ/เขียนทับ** | ไม่เข้าใจว่าคำสั่งแตะไฟล์อะไร | ไม่รัน — ให้อธิบายก่อน แล้วลองกับสำเนา | พังครั้งเดียวกู้ไม่ได้ถ้าไม่มี backup |
| **ข้อมูลตัวอย่างให้ AI** | ต้องให้ AI เห็นหน้าตาไฟล์ | ข้อมูลปลอม / แค่หัวคอลัมน์ | ข้อมูลคนไข้จริง/API key ในแชตสาธารณะ = รั่ว (PDPA) |

## ผลงานที่ต้องส่ง
> ผลของ skill นี้ = **prompt สั่งงานที่ครบชั้น** + **โค้ดที่ผ่านด่านตามระดับความเสี่ยง** (ไม่ใช่แค่ "โค้ดที่ AI บอกว่าใช้ได้")

**ขั้นตอน (มีด่านทุกขั้น):**
1. เติม template ข้างล่างให้ครบทุกบรรทัด → ด่าน: มี "ตัวอย่างที่ถูก" อย่างน้อย 1 แถว
2. ส่งให้ AI → ตอบคำถามสมมติฐานที่มันถามกลับ → ด่าน: ไม่มีข้อไหนที่ AI "เดาเอง" โดยไม่บอก
3. รับโค้ด + คำอธิบาย + ผลรันกับตัวอย่าง → ด่าน: เห็นผลรันจริงด้วยตา ไม่ใช่คำว่า "ใช้ได้"
4. เทียบกับของเดิม (diff) → ด่าน: แตะเฉพาะที่ขอ
5. ตรวจตามระดับความเสี่ยง (ตารางทางแยกแถวแรก) → accept หรือถามต่อ → ผลถูกแล้ว **หยุด**

**Template prompt (คัดลอกแล้วเติม):**
```
เป้า: [อ่านไฟล์ ... → ทำ ... → เซฟเป็น ...]
ตัวอย่างที่ถูก: [input 1 แถว] → [output ที่ต้องได้]
ขอบเขต: แก้เฉพาะ [ไฟล์/ฟังก์ชัน] ห้ามแตะส่วนอื่น ห้ามจัดรูปแบบ/เปลี่ยนชื่อตัวแปรอื่น เจอโค้ดตายให้บอก อย่าลบเอง
ก่อนลงมือ: ถ้าไม่ชัด (ชื่อคอลัมน์ / ตัวคั่น / encoding ไทย / ค่าว่างทำไง) ถามกลับ 1-3 ข้อ อย่าเดา
ขนาด: ทำเวอร์ชันเล็กสุดที่ใช้ได้ก่อน ไม่ต้องเผื่ออนาคต ไม่ต้องเพิ่ม option
ส่งมอบ: อธิบายเป็นภาษาคนทีละขั้น + รันกับตัวอย่างข้างบนแล้วโชว์ผลจริง + บอกว่าอ่าน/เขียนทับ/ลบไฟล์อะไรบ้าง
```

**นิยามว่า "เสร็จ" (ตามระดับความเสี่ยง):**
- **ทุกระดับ:** ตอบ "ใช่" ครบ 5 ข้อในเช็กลิสต์ VERDICT + เห็นผลรันกับข้อมูลจริง 1 ชุด
- **เสี่ยงกลาง:** + oracle — เคสที่รู้คำตอบอยู่แล้ว (อย่างน้อย 1 เคสคำนวณมือ) ถูกทุกเคส
- **เสี่ยงสูง:** + negative control ที่ **แดงจริง** + backup ข้อมูลจริงก่อนรัน + รีวิวแยกโดยคน/AI อีกตัว
- ตัวเลข metric (เทสต์ผ่านกี่ข้อ, lint เขียว, exit 0) **ไม่นับเป็นหลักฐานว่าเสร็จ** ถ้าไม่มีผลจริงข้างบน

## กับดักที่ร้ายสุด (นอกเหนือลำดับข้างบน)
- **ผล "ดูปกติ" แต่ผิด** — AI เดาคอลัมน์/หน่วย/เกณฑ์ผิด แล้ว output ออกมาดูสมเหตุผล = อันตรายสุดกับงานแล็บ เพราะไม่มี error ให้เห็น; กันด้วยข้อ 2 + รันเทียบกับผลที่คำนวณมือ
- **เชื่อ "โค้ดนี้ใช้ได้แน่นอน" โดยไม่รันจริง** — AI มั่นใจได้แม้โค้ดพัง; ทดสอบกับข้อมูลจริงเสมอ ไม่เชื่อคำรับรอง
- **paste ข้อมูลคนไข้จริง/API key/รหัส ลงแชต AI สาธารณะ** — รั่ว+อาจถูกเก็บไปเทรน (PDPA); ใช้ข้อมูลปลอม/แค่โครงคอลัมน์ · key เก็บแยก ไม่ฝังในโค้ดที่จะแชร์ (เชื่อม digital-judgment)

## ช่องสำหรับผู้เชี่ยวชาญเติม
> เติมเคสจริงในงานคุณ เช่น:
> - *"(MT) ตอนให้ AI เขียนสคริปต์ parse ผล LIS/CSV ผมเคยพลาดเพราะมันเดา... (เช่น encoding/คอลัมน์/หน่วย) ป้องกันด้วยการสั่ง..."*
> - *"โค้ดที่ AI ชอบ over-engineer ในงานสรุปผล/QC ของผม คือ... ผมตัดออกด้วย..."*
> - *"success criteria ที่ผมใช้ตรวจก่อน accept งานวิเคราะห์ข้อมูลแล็บ คือ..."*
